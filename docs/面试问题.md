## 0. 电梯稿（30 秒版本，先背熟这段）

> 做了一套端到端的多模态视频暴力审核系统。V1/V2 是特征级方案：I3D 视觉 + AST 音频 + ASR 文本，
> 系统比较了**六个融合位置**，在 XD-Violence 4490 个片段（1715 部电影、电影分组交叉验证）上
> 拿到 F1 **0.954**；并发现一条规律——**最优融合位置随数据量滑动**：788 样本时 late fusion 最优、
> 4490 样本时 early fusion 反超登顶，在 2 模态和 3 模态上双重验证。
> V3 换成 VLM 路线：Qwen2.5-VL-7B 零样本 AUC 0.900，QLoRA 微调（0.57% 参数）到 **0.990 / F1 0.948**，
> 并且是唯一能跨域的方案（UCF-Crime 零样本 0.879，而特征迁移完全失败）。
> 最后落地成**级联架构**：小模型 Triton 部署扛 ~2500 QPS，只把置信度 [0.4,0.6] 的 1.8% 边界流量
> 路由给 vLLM 上的 VLM 深度推理——成本是全量走 VLM 的 **1.6%**。

## 一、模型选型

### Q1. 为什么用 VLM 而不是 VideoMAE？

**答题主线**：不是拍脑袋选的，是**先试了 VideoMAE、输了、才转向 VLM**——而且输的方式指明了 VLM 为什么该赢。

**第一步，我们真的试了 VideoMAE，两种用法都不如 I3D**（§4.4，诚实的负结果）：

| 方案 | F1 | AUC |
|---|:---:|:---:|
| I3D（预提取特征） | **0.897** | 0.951 |
| VideoMAE-base 特征（自监督） | 0.924* | 0.925 |
| VideoMAE-k400 特征（监督微调版） | 0.921* | 0.808 |
| VideoMAE 端到端全参微调（4 epoch） | **0.673** | 0.781 |

（*为 ⑥ cross-attn 口径下的值，与 I3D 同口径比较仍不占优。）

**端到端微调 86M 参数的 VideoMAE 崩到 0.673，是全项目最深的一课**：3.5k 样本喂不饱一个从预训练
权重开始全参更新的视频 transformer，它把预训练表征冲掉了，反而不如冻结的 I3D 特征 + 一个线性头。

**第二步，转向 VLM 的三个理由**（每个都有实测支撑）：

1. **世界知识 ⇒ 跨域能力**。特征方案跨域完全失败（XD→UCF 域探针 AUC 1.000，两个域线性可分，
   迁移等于随机）；VLM 零样本到 UCF 就有 **0.879**，Kinetics 450 条正常视频 **0 误报**。
   审核系统上线要面对没见过的分布，这条是决定性的。
2. **可解释**。VLM 能输出"画面里两人扭打、有人倒地"这样的理由，I3D+LR 只能给一个分数。
   审核业务要给人工复审看依据，这是产品需求不是加分项。
3. **稀释型漏报的结构性解法**。见 Q2 的详细分析——I3D 是"先池化再分类"，VLM 是
   "先保留全部 token、注意力在推理时自己找"，这直接解决了我们错例分析里最大的一类 FN。

**追问陷阱**：
- *"那 I3D 还留着干嘛？"* → 留着做级联第一级。它 **63µs/clip**，VLM **256ms/clip**，差 ~4000 倍；
  而且它 AUC 0.984 已经很强，90%+ 的流量根本不需要 VLM。**不是二选一，是分工。**
- *"VideoMAE 输了是不是你没调好？"* → 承认这是小数据下的结论，不是模型本身的结论。
  想让它赢需要更多数据 / 更细的帧采样 / 更大的底座（VideoMAE-L）——我们在 §4.4 明确写了这一点。
  但正因为如此，**同样是"微调大视频模型"，QLoRA 只动 0.57% 参数就没重蹈覆辙**，这个对照本身就是结论。

## 二、数据

### Q2. 视频怎么 sampling？

**答题主线**：分三层讲——特征侧怎么采、VLM 侧怎么采、**以及采样策略如何直接造成了我们最大的一类错误**。

**1) 特征侧（V1/V2）**：I3D 按 16 帧窗口滑动出 `(T, 2048)` 序列；音频 AST 出 `(T, 768)`。
喂给不同融合位置时两种用法：
- **池化成单向量**（②③④⑤ 用）：`.mean(0)`；
- **重采样成定长 token 序列**（①⑥ 用）：`np.linspace` 均匀取 32 个视觉 token / 16 个音频 token。

**2) VLM 侧（V3）**：每个片段预抽 16 帧存 npz，推理时**均匀取 8 帧**（`frames16` → 8 张 PIL）。
8 帧 × 64 视觉 token = **512 token**，加提示词约 559 token，4k 上下文绰绰有余。
为什么是 8：token 预算与信息量的折中，`min_pixels/max_pixels` 控制每帧 token 数（28×28 像素→1 token）。

**3) 关键洞察——采样稀释是我们最大的一类 FN 的根因。**
错例分析里挑了 8 个漏报逐帧核查，发现**没有一个是算法看走眼**：

| 类别 | 数量 | 例子 |
|---|:---:|---|
| 标签分类学问题（"暴力"定义太宽） | 2 | 大学化学课炔烃气球爆炸（label_G=Explosion）、路口车祸监控（label_B6=Car accident） |
| 体育视频（打架只占几秒） | 2 | NBA 直播全程正常比赛、冰球锦标赛新闻采访 |
| 标签正确但暴力 <15% 时长 | 4 | 叶问2 打斗 10 秒 / 全长 66 秒；Bourne 枪击瞬间极短 |

后两类 6 个全是**采样 + 平均池化把短暴力稀释掉了**——一个 6 分钟片段里 10 秒的打斗，
mean-pooling 之后特征里基本没有信号，9 个方法全体一致漏报。

**解法（能说出来就是加分）**：
- **片段内滑窗打分取 max**，而不是对整段取平均——这才对齐 XD 弱标签的语义（"某处出现过"）；
- 提高采样率或做**运动/音频能量引导的非均匀采样**（打斗段音频能量高，可以据此偏置采样）；
- VLM 路线天然缓解：512 个 token 全部保留，注意力可以只盯着有暴力的那一帧下结论。

**追问陷阱**：
- *"8 帧会不会漏掉暴力瞬间？"* → 会，这是**采样率问题不是聚合问题**，两者要分开谈。
  代价是可量化的：提到 16 帧 token 翻倍、延迟约翻倍，是明确的成本-召回权衡。

### Q3. Hard example 怎么定义？

**答题主线**：我们的定义是**操作性的、可自动产出的**——不是人工凭感觉挑。

**定义**：在电影分组交叉验证下拿到每个片段的 **out-of-fold 预测**（保证打分时该片段的电影
从未进过训练集），然后按错误类型取：

```
FP 误报 = 标签正常 但 p ≥ 0.5     （取置信度最高的前 N 个 → 模型最"自信地错"）
FN 漏报 = 标签暴力 但 p < 0.5
```

`error_analysis.ipynb` 产出 8 FP + 8 FN，每条带：9 个方法各自的概率表、原始帧网格、
音频波形+频谱+**可播放 MP3**、ASR 转写——人能直接判断是模型错还是标签错。

**三个层次的 hard example（讲出层次感）**：
1. **单模型错例**：某个融合位置错了 → 一般是该模态的弱点；
2. **全体一致错**（9 个方法都错）→ 真·难样本或标签问题，价值最高；
3. **方法间分歧**（① early vs ⑤ late 判定相反、跨模态冲突）→ 融合机制的边界案例。

**为什么 hard example 对微调价值最高**：它们就在**旧模型的决策边界上**，梯度信息量最大；
拿随机样本微调，大部分梯度花在模型本来就做对的样本上。

**追问陷阱**：
- *"你怎么知道不是标签错？"* → **我们真的查了**。逐帧核对后结论是：标签本身没错，
  但 XD-Violence 是**视频级弱标签**（每个视频 1~3 个类别标签，按重要性排序，
  **训练集完全没有时间定位**，只有测试集有帧级标注）。所以"标签承诺的比我们的模型假设的少"——
  它只说"某处有"，我们却当成"整段都是"在训练。这是方法论问题不是数据质量问题。
- *"hard example 会不会引入分布偏移？"* → 会，所以不能只用 hard example 训练。
  正确做法是**混入**（我们的 SFT 集是 UCF 常规样本 + hard example），
  比例过高会让模型对边界过度敏感、误报上升。

### Q4. SFT dataset 怎么构造？

**答题主线**：两路数据源 → 统一类别体系 → Qwen 对话格式 → **强制结构化 JSON 作为 assistant 目标**。

**1) 两路来源**：
- **UCF-Crime**：文件名自带类别（`Fighting033`、`Shooting008`、`Normal_Videos_308`），正则抽取即可；
- **Hard Examples**：`error_analysis` 产出的 16 个错例，XD 文件名里的 label 码映射。

**2) 类别映射（能背出官方码表是细节分）**：

| XD 码 | 官方含义 | 我们映射的审核类别 |
|---|---|---|
| A | Normal | none |
| B1 | Fighting | violence |
| B2 | Shooting | weapon |
| B4 | Riot | riot |
| B5 | Abuse | violence |
| B6 | **Car accident** | （见下方注意） |
| G | **Explosion** | （见下方注意） |

⚠️ **这里我犯过一个真实的错误并修正了**：最初把 B6 当成 gore、G 当成 weapon，
查了官方加载脚本的 `CODE2IDX` 才发现是 **Car accident / Explosion**。
这个错误同时暴露了一个业务问题：**XD 把车祸和爆炸算作"暴力"，但审核口径下它们根本不违规**
——这正是 Q2 里两个"分类学假 FN"的来源。**审核系统应该重新定义正类，而不是照搬数据集标签。**

**3) 样本格式**（Qwen VQA 对话，一行一条 JSONL）：

```json
{"conversations": [
  {"role": "system",    "content": [{"type": "text", "text": "你是内容安全审核员…违规类型仅限 violence/weapon/gore/riot/none…"}]},
  {"role": "user",      "content": [{"type":"image","image":"frames/xxx_00.jpg"}, … ×8,
                                    {"type":"text","text":"判断是否违规，只输出 JSON：{is_violating, category, reason}"}]},
  {"role": "assistant", "content": [{"type": "text", "text": "{\"is_violating\": true, \"category\": \"violence\", \"reason\": \"多人互相挥拳踢打，有人被打倒在地\"}"}]}
]}
```

**4) 清洗要点**：帧文件存在性过滤（我们 16 个 hard example 只有 2 个有帧缓存，
其余被自动跳过——**宁可样本少也不能有坏样本**）；类别均衡；reason 字段需要人工或
VLM 预标注后校验，不能留占位符进训练。

**追问陷阱**：
- *"3.3k 样本够吗？"* → 对 SFT 够（见 Q5），因为学的是口径不是知识。
  但要**教新能力**就不够——那该上 RL 或蒸馏，不是加数据量。
- *"怎么防止训练集泄漏？"* → 电影分组切分（`GroupShuffleSplit` by movie），
  同一部电影的片段绝不跨越训练/测试。这条在这个数据集上特别重要，
  因为同部电影的镜头风格、配乐、演员高度相似，随机切分会严重高估。

## 三、训练

### Q5. 为什么是 SFT（而不是 continued pretraining / RL / prompt engineering）？

**答题主线**：因为诊断结果显示**模型缺的是口径不是知识**，而 SFT 恰好是修口径最便宜的工具。

**诊断证据（这张表是全项目最会讲故事的一张）**：

| 指标 | 零样本 | QLoRA | Δ |
|---|:---:|:---:|:---:|
| AUC | 0.900 | 0.990 | +0.090 |
| AP | 0.911 | 0.990 | +0.079 |
| F1@0.5 | 0.301 | 0.948 | **+0.647** |
| Precision@0.5 | **1.000** | 0.961 | −0.039 |
| Recall@0.5 | **0.177** | 0.935 | **+0.758** |
| Accuracy@0.5 | 0.618 | 0.952 | +0.335 |
| p@top10% | 1.000 | 1.000 | 0 |

**读法**：`P=1.000 且 R=0.177` 是一个极具特征的签名——184 条暴力里它只喊了约 33 次 yes，
**但每次都对**。它不是不认识暴力（AUC 0.900 说明排序能力完好），是 P(yes) 整体压得太低。
**知识在，口径歪** → 这正是 SFT 的适应症。

**收益可以拆成两笔**：
- **校准**（大头）：F1 +0.647、Recall +0.758，主要是把两类分数分布拉开、对齐到 0.5 两侧；
- **排序**（小但最难得）：AUC 0.900→0.990 = **错排率 10%→1%，降了 10 倍**。
  这部分**阈值调不回来**——只做 oracle 阈值校准 F1 大约到 0.85，到不了 0.948。

**为什么不选其他方案**：
- **Prompt engineering**：改不了校准，我们试过人设+CoT，判定仍不稳；
- **Few-shot**：多模态示例太贵（1 个示例 = 8 帧 × 64 = 512 token，4 个示例每次调用多烧 2000+ token），
  且 few-shot 最难修的恰恰就是校准；
- **Continued pretraining**：没有那个量级的数据，且会破坏通用能力；
- **RL**：适合教长链推理/工具使用，我们的任务是单次二分类判定，杀鸡用牛刀。

**追问陷阱**：
- *"1 epoch 就够？是不是没训够？"* → epoch 末 mean_loss 已降到 0.10。
  决定 epoch 数的是**预训练底子与任务的距离**，不是模型能力：我们自己的 ① early transformer
  从随机初始化学要 **200 epoch**；BERT 下游微调只要 2-4。多 epoch 的害处很具体——
  记忆样本、输出分布变尖（**校准反而恶化**，直接伤害我们的级联路由带）、通用能力遗忘
  （1 epoch 就已观察到解释能力轻微磨损，这也是我们做 adapter 开/关两模式部署的原因）。

### Q6. LoRA 插在哪些层？

**答题主线**：**LLM 的 28 层 × 7 个线性投影，视觉塔和嵌入/lm_head 完全不动**。

```python
LoraConfig(r=16, lora_alpha=32, lora_dropout=0.05, task_type="CAUSAL_LM",
           target_modules=["q_proj","k_proj","v_proj","o_proj",      # attention
                           "gate_proj","up_proj","down_proj"])       # MLP
```

**结构上它是什么**（这里要讲清楚，是高频追问点）：每个目标层原来是 `h = W₀x`（W₀ 冻结），
LoRA **并联**一条低秩旁路：

```
h = W₀x + (α/r)·B·A·x        A: r×d_in（随机初始化）   B: d_out×r（初始化为 0）
```

- **B 初始化为 0** ⇒ 训练起点行为与底座完全一致，从零学起；
- **r=16** 是假设"任务适配所需的 ΔW 落在一个 16 维低秩子空间里"；
- **α/r = 2** 把"旁路相对底座多响"从学习率里解耦（换 r 不用重调 lr）；
- 参数账：每层 7 个矩阵 × 16×(d_in+d_out) ≈ 1.44M，×28 层 ≈ **40M = 0.57%**，存盘 **190MB**。

**⚠️ 常见误解要主动澄清**："是不是在模型外面加了一层小网络？"——不是。
它是**缝进每一层内部的 196 块并联补丁**（28 层 × 7 投影），不是外挂在最后的探头。
区别很本质：外挂探头改不了中间 28 层的计算过程；并联补丁等效于每层权重变成 `W₀ + (α/r)BA`，
**前向的每一步都被微调了**，只是改动被约束在低秩子空间里。也正因为是"同位置加法"，
训完可以 `merge_and_unload()` 把 BA 加回 W₀ 得到一个普通模型，推理零额外开销。

**为什么 7 个全挂而不只挂 attention**：QLoRA 论文的消融结论是**同等参数预算下，
覆盖全部线性层 > 只挂注意力**。q/k/v/o 决定"看哪里、取什么"，gate/up/down 决定"取到的怎么加工"。

**追问陷阱**：
- *"为什么不挂 embedding / lm_head？"* → 参数量暴涨（1.1B）、且任务不需要改词表语义。
  PEFT 里如果要挂得用 `modules_to_save`，我们没开。

### Q7. Vision encoder freeze 吗？为什么？

**冻结**。三个理由，从强到弱：

1. **数据量不匹配**：3.3k 样本对 0.67B 视觉参数是杯水车薪，硬训会冲掉预训练的通用视觉表征。
   **我们有直接证据**：§4.4 端到端全参微调 VideoMAE（只有 86M，比这还小 8 倍）就崩到了 F1 0.673。
2. **诊断显示感知没问题**：7.3 的 CoT 输出表明零样本就能准确**描述**画面内容
   （"几个人在街道上互动，背景有烟雾"）——**差的是判定口径，而口径长在 LLM 层**。
   在没坏的地方施加梯度是纯风险。
3. **省显存**：不训就不用存它的梯度和优化器状态。

**一个工程细节（说出来显得真做过）**：Qwen2.5-VL 的 ViT 内部注意力用的是融合命名 `qkv`，
而不是 `q_proj`——所以 `target_modules` 的名字匹配**天然只命中 LLM 的 28 层**，视觉塔是被
命名巧合"顺带"冻住的。换别的模型必须自己确认，不能假设。

**追问陷阱**：
- *"那视觉侧的领域差异怎么办？"* → 走两条路：提示词里给审核口径（7.3 的人设 + 类别清单），
  以及 LLM 层的 LoRA 学会"如何解读视觉 token"。实测证明够用（AUC 0.990）。
  如果视觉域差异极大（比如红外/监控画质），才需要考虑给 ViT 也挂 LoRA。
- *"视觉塔和 LLM 之间那个 adapter 呢？"* → 注意**"adapter"一词两义**：
  Qwen2.5-VL 里**串联**在通路上的是 **PatchMerger**（2×2 patch 拼接 + MLP 投影，
  1280 维 → 3584 维），属于底座本体、阿里预训练时就训好、我们也冻结；
  我们训的是**并联**在 LLM 层内的 LoRA adapter。两者位置、作用、可拆卸性完全不同。

### Q8. LoRA 和 QLoRA 的区别？

**一句话**：QLoRA = **4-bit 量化的冻结底座** + LoRA。差别只在底座怎么存，不在旁路怎么训。

| | LoRA | QLoRA |
|---|---|---|
| 底座权重 | bf16 冻结（~16.6GB） | **NF4 4-bit 冻结（~5.9GB）** |
| 旁路 A/B | bf16 可训练 | bf16 可训练（一样） |
| 前向 | 直接算 | 每 64 权重块**现场反量化成 bf16** 再算 |
| 反向 | 梯度穿过 W₀ 到 A/B | 一样（需要 W₀ 的值，但不给 W₀ 算梯度） |
| 显存 | 7B 模型约需 20GB+ | **单张 24GB 卡有余**（我们在 L4 上跑的） |

**三个技术点**（能说清楚就是深度分）：

1. **NF4 是什么**：4-bit 只有 16 个格点，NF4 把这些格点按**标准正态分布的分位数**摆放——
   因为训好的权重近似正态分布，这样格点的信息利用率最优。每 64 个权重一组共享一个
   absmax 缩放因子；`double_quant` 把这些缩放因子本身再量化一次，再省 ~0.4GB。
2. **显存账才是关键**：AdamW 给每个可训练参数存 2 份状态。全量微调 7.6B 需要 ~60GB 优化器状态；
   LoRA 只有 40M 可训练 → **~0.3GB**。这才是 24GB 单卡能 SFT 的真正原因，量化只是让权重装得下。
3. **量化误差谁来补**：底座的量化误差**有机会被旁路 LoRA 在训练中顺带补偿**——
   这是 4-bit 底座还能微调到 AUC 0.990 的原因之一。

**`prepare_model_for_kbit_training` 做了什么**（配套三件事）：LayerNorm 等敏感层留 fp32 保数值稳定、
打开梯度检查点（用重算换显存）、让输入嵌入可传梯度（否则梯度到不了 LoRA）。

**追问陷阱**：
- *"4-bit 后为什么是 5.9GB 而不是 16.6/4≈4GB？"* → 三个原因：
  ① bitsandbytes 只量化 `nn.Linear`，**词嵌入和 lm_head 不量化**（15.2 万词表，~1.1B 参数
  bf16 保留 = 2.2GB）；② 量化元数据 ~0.13 bit/权重 ≈ 0.1GB；③ 底数是 8.3B 总参数。
  对账：3.3 + 0.1 + 2.2 + 0.3 ≈ **5.9GB**，有效压缩率 ~2.8× 而非 4×。
- *"那 2.2GB 能压吗？"* → 能：int8 行量化砍半；或最激进——打分模式只读 yes/no 两个 logit，
  把 152k×3584 的 lm_head 换成 **2×3584 的分类头（1.1GB→14KB）**，正好契合我们的两模式部署。
  权重绑定（tied embedding）无损砍半，但 Qwen2.5 只在 ≤3B 型号上绑了，7B 事后绑不了。

### Q9. SFT 的 loss 是什么？

**答题主线**：标准的 **next-token 交叉熵**，但关键在**损失掩码——只在 assistant 答案段算**。

```
序列:  [system 审核员人设][user: 8帧×64 视觉 token + 提问][assistant: "yes"]
标签:  [     -100        ][            -100             ][   ✓ 算 loss    ]
```

`-100` 是 PyTorch `CrossEntropyLoss` 的 `ignore_index`。

**为什么必须掩**：不掩的话模型会花大部分梯度去学"复述提示词和视觉 token"——
那是它本来就会的东西，学了白学，还把答案信号稀释掉了。掩码后每条样本的全部梯度
都集中在那 1 个 yes/no token 上。

**打分时不走生成**（这点常被问）：我们不采样，而是取**首 token 的 yes/no logits 归一化**：

```python
P(violent) = sigmoid(logit_yes - logit_no)     # 或 exp(yes)/(exp(yes)+exp(no))
```

这样得到的是**连续、可校准、可算 AUC 的概率**，而不是一个离散的 yes/no 字符串。
训练目标（答案 token 的交叉熵）和推理读数（同一个位置的 logits）**完全对齐**——
这个一致性是整套方案能拿到 AUC 0.990 的前提。

**追问陷阱**：
- *"类别不均衡怎么处理？"* → 我们的评测集 46% 暴力，基本均衡，没做加权。
  如果极度不均衡，可以在答案 token 的 loss 上加类别权重，或做重采样。
- *"为什么不用 BCE / 分类头？"* → 那是另一条路（也是 Q8 里 lm_head 压缩那档的思路），
  会失去生成解释的能力。我们选了保留生成能力 + 读 logits 的折中。

## 四、输出与工程

### Q10. 结构化 JSON 如何保证合法？

**诚实分层回答——先说我们做了什么，再说生产应该怎么做。**

**我们做的（两层）**：
1. **SFT 把格式训进去**：assistant 目标全部是严格 JSON，模型学会了这个输出分布；
2. **打分路径根本不生成 JSON**：走首 token logits，从物理上不可能出现解析失败。
   这是最稳的一招——**能不生成就不生成**。

**生产该做的（按可靠性排序，能说出来是加分项）**：

| 方案 | 机制 | 可靠性 |
|---|---|---|
| **约束解码**（首选） | vLLM `guided_json` / outlines / xgrammar：每步解码时按 JSON Schema **屏蔽掉所有会导致非法的 token** | **100%**，语法上不可能出错 |
| 结构化输出 API | 同上的托管版本（`response_format`） | 100% |
| 重试 + 解析校验 | try/except + 最多重试 N 次 | ~99%，有延迟尾巴 |
| 后处理修复 | 正则抠 `{...}`、补引号 | 脆，不推荐作为主方案 |

**关键论点**：约束解码是**语法级保证**而不是概率级保证——它在采样时就把非法 token 的
概率置零，模型不可能"写歪"。代价是需要预编译语法（首次有编译开销）、
以及可能轻微扭曲输出分布（被屏蔽的 token 概率质量重新分配）。

**但语法合法 ≠ 语义正确**：JSON 结构对了，`category` 仍可能是幻觉值。
所以还要一层**枚举校验 + 兜底**：`category` 必须在白名单里，不在就落到 `none` 并告警。
我们在 prompt 里明确列出了类别清单（`violence/weapon/gore/riot/none`）也是为了压缩这个空间。

### Q11. Cascade threshold 怎么选？怎么校准？

**答题主线**：分两个独立的问题——**阈值选在哪**（业务问题）和**分数值得不值得信**（校准问题）。

**1) 我们的做法与实测**：置信度落在 **[0.4, 0.6]** 的路由给 VLM。实测（964 条测试集）：

| 指标 | 数值 | 说明 |
|---|:---:|---|
| 路由带流量占比 | **1.8%**（17/964） | VLM 只吃这么多 |
| 小模型**在带内**的准确率 | **0.41** | 比随机还低——证明这个带确实是混淆区 |
| 小模型整体 AUC / F1 | 0.984 / 0.932 | 带外它很能打 |
| 成本：纯小模型 / 纯 VLM / 级联 | 0.02s / 279s / **4.54s** | 级联是纯 VLM 的 **1.6%** |

**"带内准确率 0.41"是验证阈值选对了的核心证据**——如果带内准确率还有 0.9，
说明这个带里小模型明明能判对，路由给 VLM 是浪费。

**2) 阈值该怎么科学地选（不是拍 0.4/0.6）**：
- **按容量反推**（最实用）：VLM 吞吐 ~4 QPS，总流量 X QPS，能承受的路由比例 = 4/X，
  从置信度分布的分位数反查出对应的带宽。**先定预算，再定阈值。**
- **按边际收益**：扫描不同带宽，画"带宽 vs 净修正数"曲线，取边际收益跌破成本的点；
- **非对称带**：审核场景漏放代价 >> 误标代价，所以带应该**向低分侧偏移**（比如 [0.3, 0.6]），
  宁可多送一些"看起来正常"的去复审。

**3) 校准——两件不同的事**：
- **校准分数**：小模型是 LR，本身校准还不错；若换成树模型或神经网络需要
  **Platt scaling / isotonic regression**（在独立验证集上拟合），否则 "0.5" 不代表 50% 概率，
  `[0.4,0.6]` 这个带就失去了意义。**校准是路由带能成立的前提。**
- **校准指标**：ECE（Expected Calibration Error）、可靠性图（reliability diagram）。
- 我们在 §4.8 做过专门的阈值校准分析：oracle 阈值能把 F1 从 0.370 拉到 0.534，
  但**加标签（改进模型本身）能到 0.679**——**校准能救回一部分，但救不回全部**。

**追问陷阱（这题最容易被追打）**：
- *"你这 17 条样本，结论有统计意义吗？"* → **没有，我必须承认**。17 条里只有 3 条有帧缓存
  真正送了 VLM，结果是"修正 1 个、引入 1 个新错"——**净收益为 0，样本量太小说明不了任何事**。
  这个实验证明的是**工程链路通了和成本模型成立**，不是质量收益。要证明质量收益需要
  扩大带宽或补齐帧缓存重跑，这是明确的 next step。
- *"1.8% 的带是不是太窄了？"* → 是。因为我们的小模型太强（AUC 0.984），
  置信度分布两极分化。真实生产流量分布更脏，带会宽得多——所以**容量规划要按真实流量的
  分布重做，不能照搬这个 1.8%**。

### Q12. vLLM 的 PagedAttention / continuous batching 怎么工作？

**PagedAttention**：把 KV cache 切成固定大小的 block（默认 16 token/块），
像操作系统的**虚拟内存分页**一样按需分配 + 用页表索引。
- **解决什么**：传统实现给每个请求预分配 `max_seq_len` 的连续显存，实际用不满 →
  内部碎片 + 外部碎片，业界测算 **60-80% 的 KV 显存是浪费的**；
- **收益**：同样的卡装下大得多的有效 batch；且 block 可以在请求间**共享**
  （相同前缀只存一份，我们所有请求的 system prompt 完全相同，是 prefix caching 的理想场景）。

**Continuous Batching**：调度粒度是**"一步生成"而不是"一个 batch"**。
- 传统静态批处理：整批一起进、一起出，**整个 batch 等最慢的那条**，先完成的 GPU 位置空转；
- 连续批处理：每完成一步就重新调度——新请求随时插进正在跑的 batch，
  完成的请求立刻退出让位。GPU 不再等最慢的样本。

**我们的实测（L4 24GB，24 个片段）**：

| 测量 | 数值 |
|---|---|
| 冷启动：batch=1 → 整批 24 | 1288 ms/clip → 279 ms/clip，**4.6×** |
| 预热后：batch=1 → batch=24 | 122 ms/clip → **29 ms/clip，4.2×** |

**一个必须主动说明的细节**：我们的负载只生成 **1 个 token**（yes/no），
耗时几乎全在 **prefill**（8 帧视觉编码 + 提示词前向）。所以这里的收益主要来自
**prefill 的批内并行 + 调度开销消除**，而不是 continuous batching 最擅长的 decode 阶段。
如果是 7.3 那种 CoT 长文本生成，"先完成先退出"还会再叠加一层收益。
**能主动区分这两种收益来源，说明是真的理解而不是背概念。**

**冷热差 10 倍（1288 vs 122ms）的教训**：首批请求含 CUDA kernel 编译、图捕获、缓存预热，
**任何压测必须先热身**，否则数字没意义。

**追问陷阱**：
- *"你的 profiling 显示 SM 利用率从 62% 降到 22%，不是说批处理该提高利用率吗？"*
  → **这是我们测量方法的缺陷，我承认**。`vlm_score` 把 CPU 侧的预处理
  （加载 24 个 npz、PIL 转换、processor tokenize）算在了计时区间内，
  整批阶段大量墙钟时间花在 GPU 空转等 CPU 预处理上，NVML 采样到的自然是低利用率。
  **正确做法**是把预处理移出计时区间、或用 vLLM 自带的 metrics（`gpu_cache_usage_perc`、
  吞吐计数器）而不是 NVML 粗采样。延迟数字（4.2×）是可信的，利用率数字不可信。

### Q12b.（延伸）Triton 那一级怎么部署的？

**目录即契约**——Triton 不用写服务代码：

```
model_repository/fusion_concat_lr/
├── config.pbtxt          # backend/输入输出/dynamic_batching/instance_group
└── 1/model.onnx          # 版本目录，放 2/ 即灰度
```

**实测（256 条真实特征，L4 box）**：

| 测量 | 结果 |
|---|---|
| 正确性 vs 本地 onnxruntime | **逐位一致**（diff = 0.0） |
| batch=1 HTTP 串行 | mean 1.17 ms，p99 1.45 ms |
| 并发 1→4→16→64 | 934 → 2172 → 2430 → **2463 req/s** |
| batch=256 单请求 | 59.5 ms（232 µs/clip） |

**两个真实的坑**（讲出来比讲成功更可信）：
1. **opset 错位**：skl2onnx 默认导出 opset 22，镜像里的 onnxruntime 只支持到 21 → 加载失败。
   修复：`to_onnx(..., target_opset=21)`。**导出方和部署镜像的 opset 支持范围必须对表。**
2. **tritonclient 的 HTTP 客户端基于 gevent，不可跨线程共享**——并发压测每个线程必须
   建自己的 client，否则 `greenlet.error: Cannot switch to a different thread`。

**级联架构的物理基础**：低耗流 ~2500 QPS vs 高耗流 ~4 QPS，**差 ~600×**。
这个数量级差就是级联能省 98.4% 成本的根本原因。

### 闭源（作为质量上界参考 / 不可用于敏感数据）

- **GPT-5 系列**：综合推理最强梯队；
- **Gemini 2.5 Pro**：**原生长视频**（上下文可达百万级 token，能直接吃整段视频而非抽帧），
  如果不做本地部署、只求效果，长视频审核这是最强的；
- **Claude**：文档/图表理解与长文本推理强，安全对齐严格。

**我们为什么不用闭源 API**（这是选型题的标准答案）：
审核场景的数据是**用户上传的违规内容**，把帧传给第三方往往直接不合规；
且成本随流量线性增长，而我们的级联架构把 98.4% 的流量挡在了 VLM 之前——
**本地部署的边际成本优势在高流量下压倒性**。

### 选型方法论（比背模型名重要）

1. **先定部署约束**：本地 vs API、显存预算、许可（Apache/MIT vs 研究限定）；
2. **再定模态需求**：多帧视频 / 长视频 / OCR / grounding —— 我们需要多帧 + 中文场景；
3. **最后才比榜单**：且要比**你的任务上的**表现。我们自己的实测是最硬的依据：
   同一批帧上 Qwen2.5-VL 零样本 **AUC 0.900** vs CLIP 零样本 **0.825**——
   **VLM 的世界知识确实比 CLIP 的对比学习表征更能处理"暴力"这种需要语境判断的概念**。

## 六、面试官最可能挖的坑（主动准备好，诚实作答）

这一节的价值在于：**主动承认边界比被问倒强得多**，而且能展示方法论成熟度。

| 弱点 | 诚实答法 |
|---|---|
| **级联质量收益未证明** | 17 条带内样本、3 条真正送 VLM、净收益 0。工程链路和成本模型验证了，**质量收益没有统计意义**，需要扩带宽重跑 |
| **SM 利用率数字不可信** | 计时区间包含 CPU 预处理，NVML 粗采样被污染（见 Q12）。延迟数字可信，利用率数字要重测 |
| **prompt 没做版本化评测** | 所有量化结论建立在**单一 prompt 版本**上，没做 A/B。正确做法：固定 400 条留出集，dev 子集迭代、held-out 只报一次，比 AUC/F1/**ECE**，成对 bootstrap 检验 |
| **跨域迁移失败（特征侧）** | 域探针 AUC 1.000，同切分消融显示混合训练 = 单域，**我提出的 scaler artifact 假设被 per-domain z-scoring 实验证伪了**——这是个诚实的负结果 |
| **数据集标签口径** | XD 把 car accident / explosion 算暴力，审核口径下不该算。**正类定义应该按业务重定义**，不是照搬数据集 |
| **弱标签 vs 强假设** | 训练集只有视频级标签无时间定位，我们却按"整段=标签"训练，这是稀释型 FN 的方法论根因。解法：滑窗取 max |
| **n=400 的置信区间** | AUC 的 CI 约 ±0.01，0.990 和 0.985 之间不做文章。所有对比都在**同一批样本**上成对做 |
